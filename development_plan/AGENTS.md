# Agent instructions — deTour scaffolding game controller

## Mission
Build the **Windows PC game-controller application** for the deTour scaffolding exhibition. The PC coordinates one UR10e robot moving three floorboards among four zones; up to four NFC-localized, line-following toy cars; the single USB HID gamepad tested in E2; a USB-connected BLE modem; and four visitor displays. Implement incrementally against available real hardware, using focused dry-run or synthetic substitutes when necessary.

## Read in this order
1. `SYSTEM_SPEC.md` — agreed functional behavior and constraints.
2. `INTERFACES.md` — frozen interface policy, canonical source and approved topology-byte clarification.
3. `MILESTONES.md` — incremental implementation, test gates, available hardware.

## Non-negotiable boundaries
- **Current transport is USB serial to a Bluetooth Low Energy (BLE) modem, then BLE to cars. NOT ESP-NOW.** Earlier ESP-NOW examples in the repository are obsolete experiments.
- **This project's implementation scope is the PC game controller and associated PC tools.** Do not edit, flash, rewrite, or extend the car firmware or modem firmware without the user's explicit approval.
- **Keep the tested E15 PC–modem–car protocol intact.** Preserve seven-byte BLE World State; 21-byte car telemetry; serial framing, widths, byte order, sequence/echo fields, and movement-byte semantics. Only the agreed semantic interpretation of the existing `topology_id` byte may change. Do not silently add a field, a message type, new acknowledgments, or reformat old packets.
- World State packing is `<HB4B` (7 bytes); E15 Robot State packing is `<BHHB4sHBBBhhH` (21 bytes). The three `B` fields after NFC age are line sensors, controller state and line-follower state. The earlier 20-byte Python format was a documentation typo, not a firmware or wire-format change.
- If a requested feature requires firmware or wire-interface changes, stop that implementation, explain the conflict and request explicit authorization unless already given. The proposed E16 delta only removes E15's map-specific tag-cycle restriction; map/intersection/reservation enforcement remains on the PC. A firmware-change brief is authorized documentation, not implementation/flashing permission.
- The tested E15 firmware is the implementation truth for current behavior; requirements describe the intended system. Label gaps clearly rather than claiming they are already implemented.
- No movement of the real UR robot without explicit operator authorization, validated poses, a verified clearance procedure, and an appropriate live-mode test plan. The robot's certified safety functions are separate from PC logic. Protective-stop auto-reset policy remains unresolved and must not be silently implemented.
- Do not command live motion using placeholder target positions. Do not treat development-mode screwdriver completion as proof of successful mechanical attachment.

## Working method
- Start hardware/communication experiments with a simple, minimal working file using the underlying library directly and a harmless request/reply test. Add wrappers or adapters only when needed, after the initial script works; verify each layer against that baseline. Isolate failures one layer at a time before adding motor commands or power-cycle logic.
- **Before implementing each milestone:** inspect related existing code, identify assumptions, explain the concrete architecture and tests in a short plan, and obtain the user's approval to proceed. In particular, discuss any new firmware/interface expectations and the Rhino NFC registration workflow at its milestone.
- Keep business logic independent of physical I/O and display rendering. Prefer small replaceable adapters (real or synthetic) rather than a comprehensive physics simulator. Ensure one real car can be used while other cars are designated Not Present or fed synthetic test events.
- Preserve working subsystems; avoid unnecessary rewrites. Keep configuration in INI or clearly documented data files. The modem's fixed COM port is read from INI; failed initial opening is fatal, displaying configured and available ports. Reconnect the modem only to that configured port during normal running. These COM rules do not apply to the USB HID gamepad.
- Use Pygame's joystick API and E2's tested input handling. Read each car's `forward_button`, `left_button` and `right_button` from `[car_N_control]` in `config/address.ini`; do not invent a joystick serial protocol or use the legacy `[joystick]` COM metadata as HID identity. Use E2's default joystick index 0: only one gamepad is connected. Reuse its device-added/removed handling, instance-ID tracking and reconnect retry. Held inputs resume immediately after recovery once fresh input/communication and existing drive-eligibility checks pass; no release/fresh-press gate.
- Keep control loops independent and nonblocking. **The agreed PC control loop polls the gamepad and generates/submits the shared World State together at 50 Hz (20 ms).** E2's 100 Hz experiment is not the production cadence. Display redraw remains independently paced at 30/60 fps; never wait for a display/video frame before processing control. Car telemetry is **20 Hz**; the car's internal motor-control loop is 100 Hz.
- Provide structured timestamped diagnostics; show effective car commands, topology byte, car telemetry age, world-sequence echoes, per-zone owner/reservation state, robot state, and decisions.
- Require observable acceptance checks with log evidence, not merely compilation. Where a physical test is inappropriate or unavailable, use a small synthetic event sequence and say so explicitly.
- Before changing any contract, compare the current published documentation with `src/e15/car` and report differences to the user for approval.

## Scope versus deferred work
The PC application includes device adapters, startup/admin procedures, car command filtering, topology/reservation management, board scheduler, robot task orchestration, video/HUD/minimap, and logging. Separate later workflows include Rhino/Grasshopper map export, NFC registration, and UR target teaching. Their high-level contracts are in the specifications; detailed UI/data structures must be reviewed with the user before implementation.

## Initial task
**M0 is review and planning only:** audit current source and interfaces, identify verified capabilities and intended-but-missing features, propose module boundaries and real-device test strategy, and request approval before implementing M1.

## Additional agreed decisions
- No extra drive-enable/disable switch: normal mode uses current joystick intent; admin mode uses the selected car's current keyboard intent. Retain presence/freshness/protection and quit-pending stop rules. A STOPPED report alone must not prevent sending deliberate operator forward/MANUAL requests; E15 may require them to clear its own post-NFC interlock. Do not auto-drive, reboot or bypass firmware protections. See `../docs/M1_UNRESPONSIVE_CAR_REVIEW.md` for the observed incident and proposed separate firmware review.
- M1 overlay revision (2026-11-09): exactly four visible display windows; admin controls exist only as top overlays in admin mode. Other cars show "Paused by Admin" on grey; the selected car shows "Controlling by Admin" on dark orange, dark red while Left Ctrl selects MANUAL/direct control. Repeat non-car diagnostics, keep car-specific data on its own screen, and start in admin mode. Q opens an all-screen Enter/Escape confirmation and suppresses driving while pending. M1 confirms directly; production confirmation waits for verified robot HOME when robot ownership is implemented.
- Agreed M1 policies (2026-11-09): use configured Space admin toggle / Escape cancel. Leaving admin or recovering gamepad/car communication resumes immediately from fresh current held inputs, without requiring release/new press; existing fault/freshness/zone eligibility still applies. Missing modem or gamepad at initial startup shows the detailed error and quits; do not add a stay-open diagnostic exception. Runtime disconnects retain the agreed reconnect behavior.
- Preserve current E15 handling of simultaneous turn bits; no firmware change is needed. The PC filters incoherent physical input before producing movement bytes. Do not reopen firmware tie-breaking as a prerequisite; distinguish conflicting visitor input from deliberately encoded edge/center-following commands.
- Keyboard and mouse belong to the administrator only. Space toggles normal/admin mode; Escape cancels the current admin action. In admin mode ignore visitor gamepad commands, keep video/UI updating, and show "Game Paused / Admin Control" on all visitor screens. Number keys 1-4 select a car; Up/Left/Right control it in AUTO, while held Left Ctrl selects MANUAL with Down available for reverse. Read shortcuts from the existing `[admin_keyboard_shotcut]` INI section. No new firmware behavior is implied by PC admin mode or topology bit 4.
- Provide a controlled application exit that waits for verified robot HOME before closing. Do not reuse E9's immediate Escape/Q/group-exit behavior. Resolve interrupted tool/board handling and unavailable-robot cases with the operator when implementing shutdown; never force a home trajectory from an unknown state.
- Discuss recovery separately at each component's implementation: prefer silent recovery for ordinary disconnects while retaining diagnostics. Prioritize cars powered off for charging and returning after charging. Do not interpret temporary disconnection as the operator's Not Present assertion, clear reservations automatically, or invent new session fields.
- Defer map details until the user supplies tag/property JSON distilled from Rhino. Preserve the agreed 2-3 redundant approach tags per split; do not invent the final schema or exporter now.
- Navigation is a PC-only UID-to-attributes lookup, not a graph. Use `track`, `mergeedge`, `split`, `adminsplit`, `inzone`, `reservezone`, `safeexit` as defined in SYSTEM_SPEC. Distinct UID replaces context; same UID does not retrigger transitions. Denied zone requests retry each control tick without resetting granted-token timers. A new tag with both `inzone:none` and `reservezone:none` releases the token, including actually observed unknown UIDs (all-none attributes). No-read sentinels/telemetry loss do not count as unknown tags. Normal mode forces adminsplit safe exits; admin lifts that restriction but still requires tokens for zone splits. Evacuation forces safeexit in approach, forward without forced turn inside (mergeedge still applies), until the same release predicate is observed. Preserve the user's accepted single-line-road behavior when steering-reset tags are missed; do not impose a graph/firmware map requirement.
- Plan a small, bounded screwdriver communication/behavior experiment before main tool integration. Documentation of this experiment is not permission to move the UR, flash firmware or run unreviewed live tool commands.
