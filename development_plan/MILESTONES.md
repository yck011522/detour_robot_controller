# Development milestones and hardware-in-the-loop acceptance gates

**Approach:** small, working PC-controller increments tested against real devices wherever feasible. A simulation framework is NOT a prerequisite. Allow per-subsystem synthetic inputs and dry-run outputs, integrated into the same production application. Each milestone starts with a short review/plan approved by the user and finishes with reproducible evidence.

## Hardware already available (at planning time)
- Windows PC; tested USB/BLE modem; **one built car** with E15 firmware (remaining car-controller availability still to confirm); the **USB HID gamepad tested in E2**, with four three-button mappings in `config/address.ini`; **all four monitors and H.264 camera streams working in E9**; UR10e and its tested URCap/RS-485 screw-driving tool.
- STILL TO CONFIRM / COMPLETE: remaining cars and full physical button validation; complete track with ~300 NFC tags; final board installation hardware and target poses, full stall-engagement tests. Four working video feeds do not establish four completed car controllers.
- Robot should remain **motion dry-run** through car navigation/reservation and scheduler development. Real screw actuator can be tested independently with safe bounded commands. No live assembly with placeholder positions.

## M0 — Repo audit, agreement on architecture (no modifications)
**Agent tasks:** inspect current E15 car source, official protocol Markdown, modem behavior, E2 HID input and existing UR/E9 code; identify actual tested versus intended features. Validate the immutable PC–modem–BLE–car protocol, including World State `<HB4B` (7 bytes) and corrected Robot State `<BHHB4sHBBBhhH` (21 bytes). The telemetry format correction is documentation-only and matches the packed E15 structure. Propose PC modules, device abstraction/dry-run adapters, logging, test harness and priorities. Explicitly list missing information rather than invent details.
**Acceptance:** reviewed architecture + compatibility matrix; user approves M1 plan. No firmware edits or robot motion.

## M1 — PC communication, real joystick, basic diagnostics
**Build:** INI-configured modem serial port; fatal modem startup error with available COM list; fixed-port modem reconnection during operation. Use E2's USB HID gamepad via Pygame, load `[car_N_control]` button mappings from INI, and validate input-device availability/mapped indexes at startup. Use E2's default index 0 for the sole gamepad and its existing instance-ID/lifecycle/retry pattern. Discuss input reenable details when implementing recovery. Poll the gamepad and assemble/submit World State together at **50 Hz (20 ms)**, independently of display redraw. Parse/validate/log **21-byte** car telemetry at nominal **20 Hz**, using `<BHHB4sHBBBhhH`. Expose effective AUTO movement bits and received/echoed sequences. Car presence switch and synthetic car adapter; diagnostic GUI or simple debug display.
**HIL:** one real E15 car, modem and the E2 HID gamepad with available physical buttons; others Not Present/synthetic when needed. Verify all configured button mappings as hardware permits, input→motor and held/neutral behavior, HID versus modem reconnects, packet/timing statistics and continued 50 Hz control under independently paced display load, without modifying E15.
**Acceptance:** repeatable controlled motion, validated packet encoding against existing docs, telemetry loss/return behavior, startup failure procedure, log evidence. Obtain user approval before M2.

## M2 — PC tag-attribute navigation and minimal intersection test
**Build PC:** review Rhino JSON serialization, then load `track`, `mergeedge`, `split`, `adminsplit`, `inzone`, `reservezone`, `safeexit`. No navigation graph or firmware dictionary. Start with a minimal direct one-car/tag/input-to-command experiment before adding wrappers. Distinct UID replaces complete context; same UID does not retrigger transitions. Unknown observed UIDs become ordinary/all-none; no-read sentinels and stale/malformed telemetry do not. Apply SYSTEM_SPEC's split/default-edge table, merge forcing, normal-mode adminsplit safeexit and admin AUTO choices. Normal zone splits still require tokens in admin mode. MANUAL retains direct wheel control.
**Firmware boundary:** E15's fixed eight-tag checks block arbitrary exhibit tags. `E16_FIRMWARE_CHANGES.md` describes removing that map-specific constraint while preserving movement semantics, NFC hardware recovery, watchdog and packets. No local map/topology enforcement. Firmware implementation/flashing require separate authorization.
**Acceptance:** demonstrate one physical split with redundant approach tags and ordinary downstream tags; measure UID-to-command/echo timing and actual branch behavior. Cover neutral defaults, merging, adminsplit in both modes, skipped reset tags on ordinary single-line roads, unknown UIDs and repeated telemetry. Integrate token cases with M3. Use synthetic events where needed and label them; real acceptance requires the E16 baseline and physical setup.

## M3 — Reservations, topology acknowledgment and evacuation
**Build:** centralized per-zone ownership, per-car token, board occupancy and topology bits; robot pending acquisition, closure-consistent movement commands, first changed `world_seq` and wrap-safe receipt echo. Preserve presence/disconnect rules. Retry denied requests every 50 Hz tick while `reservezone` persists, allowing a stopped car to wait. Release on a new UID with `inzone:none` AND `reservezone:none`, including unknown observed tags. Admin never bypasses normal zone admission. Inactivity 10 s and hard hold 60 s evacuation timers start at first token grant, without reset on retries/repeated approach tags. Evacuate with forward+safeexit in approach; forward without forced turn inside except mergeedge; end at the same release predicate. Retain bounded failure handling.
**HIL:** one real car where possible, synthetic events for other cases, robot dry-run. Validate same-tag denied request later granted; repeated approaches without timer reset; known/unknown release; approach tags and no-read/telemetry loss not releasing; admin zone denial; both evacuation contexts; car/robot ordering and closure-consistent snapshots. Receipt echo does not establish physical clearance or firmware topology enforcement.
**Acceptance:** state transition log, tests of acknowledgement and absence policy, no contradictory ownership in modeled state, human review of explicitly accepted timing race.

## M4 — Robot scheduler and workflow dry-run
**Build:** include controlled-shutdown dry-run: stop scheduling new transfers and wait for verified robot HOME before exit; exercise held-board and blocked-shutdown cases with synthetic events. Discuss recovery/exit details here. Add startup board-inventory UI (exactly three among A-D+gripper), car-outside confirmation, board+gripper invariant; queue ordered by least recently touched and updated on successful operations; choose eligible board pickups and empty placements; replaceable selection policy; robot state-machine dry-run that exercises all high-level operations and fault/restart bookkeeping. Teach-target module stores placeholder six-joint targets with explicit calibration status, calculates high/low Z-offset waypoints via FK/IK but never authorizes live assembly with placeholders.
**Acceptance:** at least 20 repeatable moves (including baseline A→D, B→A, C→B, D→C cycle under no interference), tests of car reservations, blocked pickup fallback, startup with board held and recovery from partial states; no physical UR motion.

## M5 — Real end-effector diagnostics, then controlled UR primitives
**Prerequisite experiment before main tool integration (may be planned during M1/M2):** plan a small, separately reviewed screwdriver behavior/communication experiment using the existing URCap/RS-485 path. Establish actual commands, status/stall reports, timeouts and cancellation before designing the production adapter. Use real tool commands with motion dry-run. Test command acceptance, direction, stop and status. Explicit development mode for bounded time/rotation tests **without asserting physical stall-verified pickup**; protect hardware and log mode.
**Later live task:** after floorboards, installation points and fixtures exist, teach/calibrate targets; verify payload mass/CoM, clearance envelopes, approach trajectory and end-effector operations; integrate slow force-controlled pickup/placement and Z-depth/stall conditions in carefully authorized tests. Define fail/recovery admin primitives. Do not implement automatic protective-stop reset without separate safety review and user decision.
**Acceptance:** instrumented UR motion log, validated taught poses, force limits, and explicit supervised physical tests; independent test of fault paths. Real robot coordination with cars only after M3/M4 passes.

## M6 — Displays and visitor/admin UX
**Build:** implement agreed keyboard/mouse admin behavior: Escape toggles admin/normal; public input is ignored in admin; all visitor screens show Game Paused / Admin Control while video/UI continue. Keys 1-4 select a car; arrows provide AUTO control; held Left Ctrl selects MANUAL with reverse. Q requests verified-HOME exit, not immediate quit. Reuse the tested E9 four-screen H.264 video/rendering path; add four dedicated layouts with shared axonometric minimap, per-screen highlight/ghost cars, static tag sprite positions, board states, contextual intersection graphic, raw HID joystick visualizer and later telemetry overlays. Admin panel for car presence, startup, diagnostics, mode, fault controls and view state. All four real monitors are available. Rendering at 30/60 fps remains isolated from the shared **50 Hz gamepad-poll/World State** control path; adapt E9's prototype group-stop behavior to the agreed production fault policy.
**Acceptance:** responsive driving video on available monitors; no stalls in modem/control loop from video delays; proper own-car highlighting and no interpolation of marker positions.

## M7 — Rhino/Grasshopper map and wireless NFC registration (independent workflow)
**Do NOT code until the user-provided Rhino JSON is reviewed.** Export a PC-only UID-to-attributes dictionary with the seven agreed navigation fields and optional minimap position/orientation; no graph, adjacency, routing or firmware dictionary. Retain the proposed handheld workflow: scan, associate pending UID with a Rhino block, validate duplicates and persist/export PC data. Discuss Rhino Python vs Grasshopper, scanner protocol/addressing and modem ownership before coding. No unauthorized firmware changes. Attribute/layout changes must not require car reflashing or renumbering registrations.
**Acceptance:** small registration/export trial; stable associations after Rhino/property edits; uniqueness/attribute validation and unregistered-marker report. Unknown runtime UIDs still use ordinary/all-none behavior. Integrate full map once fabricated.

## M8 — Full exhibition integration and endurance
**Build/test:** prioritize cars powered off for charging and returning afterward, with reservation reconciliation and agreed control reenable. Verify exit waits for actual robot HOME and stays blocked on unresolved faults. Test the full set of cars/screens/joysticks when available; robot, tool, map, admin and display integration; config validation; reconnects; protective stops, stalled tool, telemetry gaps, skipped tags, batteries, simulated absent cars; operator handbook. Perform extended supervised run and fix observed defects. Maintain log/event replay useful for debugging without full physics simulation.
**Acceptance:** sign-off checklist for each interface, verified starting/homing and interruption handling, accepted residual risks, complete set of working hardware and repeatable operator setup.

## General milestone gate
At each milestone the coding agent shall deliver: (a) short design discussion before coding, (b) changed-files inventory, (c) interface-compatibility statement, (d) real-HIL versus synthetic test distinction, (e) results/log excerpts, (f) remaining unresolved questions. Never silently treat deferred features or firmware-dependent checks as passed.

## Recovery discussion checkpoints
Ask component-specific questions at implementation, preferring silent automatic recovery with diagnostics. Do not invent one universal reconnect policy.
- **M1 gamepad/modem:** held-input and reenable behavior, fixed modem-port reconnect. Gamepad selection is already agreed as E2 index 0.
- **M1/M3 cars:** charging power-off/reappearance, reboot/sequence ambiguity, fresh localization/topology and retained reservations.
- **M4/M5 robot/tool/shutdown:** interrupted operations, board attachment state, verified HOME, unavailable robot and blocked-exit/operator intervention. Discuss robot scheduling behavior during admin mode here.
- **M6 displays/admin:** independent window/video recovery, keyboard focus/routing and mode/car-selection transitions. E9's immediate group exit is not the production policy.

Discuss startup/admin interactions early enough for M1/M4; final visual layouts can remain in M6. Preserve firmware simultaneous-turn behavior and sanitize physical inputs on the PC; no firmware change is required for that case.
