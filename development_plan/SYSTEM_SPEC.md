# deTour scaffolding game controller — functional specification

**Status:** working requirements baseline, updated 2026-11-09 for PC-owned tag-attribute navigation. This document records intended behavior, including the proposed E16 changes in `E16_FIRMWARE_CHANGES.md`. It is not authorization to modify or flash tested firmware.

## 1. Purpose and physical system
A Windows PC coordinates a UR10e robot that repeatedly transfers **three identical floorboards among four installation zones (A–D)**; four independent visitor-operated line-following cars on the scaffolding, up to four dedicated FPV displays; the single USB HID gamepad tested in `experiments/e2_gamepad_controller.py` for all player inputs; a USB-serial BLE modem which relays World State to cars and telemetry to the PC; and a screw-based robot gripper commanded through an existing URCap/RS-485 path. Car 1 alone accesses Zones A,B; Car 2 alone accesses Zones C,D. Cars 3 and 4 have no movable-board zones. Each zone may be used by the robot or its designated car, never both at once.

## 2. System ownership and modules
- **Device adapters:** USB HID gamepad through Pygame, BLE modem transport, robot motion/UR controller, URCap screwdriver, FPV video sources, displays. Physical-device and synthetic/dry-run variants must expose comparable application-level contracts.
- **Central game state:** authoritative board location (A–D, gripper), robot operation phase, per-car presence/telemetry/location/reservation, zone ownership, effective availability bits and World State version/sequence tracking.
- **Car command filter:** transforms raw three-button input (forward, left, right) into effective movement byte by operating state, NFC approach context and branch restrictions. Turning rules are intersection-contextual, **not direct raw joystick passthrough**.
- **Zone manager:** four small, centrally executed state machines; car reservations at approach markers; robot pending request, topology closure, acknowledgement and robot ownership; zone-clear release.
- **Pickup scheduler:** replaceable least-recently-touched queue; eligibility is determined independently of preference.
- **Robot task executor:** reusable validated motion primitives and tool coordination, invoked by scheduler or context-limited administrator recovery.
- **Presentation:** four separately rendered screens, shared map/game model; video and rendering cannot block control loops.
- **Diagnostics and logging:** record all state changes, faults, commands, World State submissions/echoes and reservations with monotonic timestamps.

## 3. Modes, startup and shutdown
There is **STARTUP → NORMAL_OPERATION**; no separate READY state is required. Administrator mode is an input-control overlay on normal operation; controlled exit waits for verified robot HOME. Subsystems may be paused, disconnected or faulted independently without necessarily stopping the whole exhibition. Controlled shutdown is required, with the behavior in section 12; don't infer that PC software replaces UR safety functions.

Startup gates:
1. Read INI. Connect the configured **modem COM port** and initialize the **USB HID gamepad through Pygame**, validating the `[car_N_control]` button mappings. If either is unavailable, report the failure and **quit**: include configured/available COM ports for modem failure, or enumerated gamepads and mapping errors for input failure. No joystick COM connection or serial framing is involved. Use E2's default joystick index 0 because only one gamepad is connected; no automatic COM-port selection UI.
2. Establish and diagnose UR and its existing URCap/RS-485 gripper communication. Test availability without unintended motion.
3. Administrator selects **exactly three** board locations among checkboxes `A`, `B`, `C`, `D`, `GRIPPER`. That is the authoritative initial board inventory.
4. Perform **operator-assisted homing**: the operator visually verifies clearance and authorizes carefully controlled robot motion to a known home waypoint. Account for held-board geometry and payload. Block startup until homing succeeds. Homing after a restart does not automatically resume interrupted trajectories.
5. Administrator visually confirms **both token-participating cars are outside zones**, initializing their car reservations to `None`. Presence/Not Present is independently selectable per car; Not Present means physically removed, explicitly confirmed by operator.
6. Compute initial zone availability; broadcast and synchronize topology for relevant Present cars as applicable. Only then start NORMAL_OPERATION.
7. If gripper holds a board, enter `SELECT_PLACEMENT`; else enter `SELECT_PICKUP`. When starting with a held board, either of the two empty zones may receive the first placement; no unknown source zone needs exclusion.

During normal operation, modem port loss is **auto-retried only on the configured COM port**. Gamepad disconnection/reconnection is handled through Pygame's HID/joystick lifecycle as in E2, using the single device at index 0. After recovery, resume immediately from freshly sampled held inputs once existing drive-eligibility checks pass; no release-before-resume gate. Robot assembly may continue when joystick or modem communication fails, subject to independent robot state and reservation rules.

## 4. Car presence, telemetry and command flow
- **Present**: telemetry expected; missing telemetry retains last known NFC/zone reservation; warning displayed after configurable threshold. If last known outside and no reservation, robot may acquire the zone without fresh acknowledgment (deliberate operational trade-off). If last known approaching/inside, retain reservation. When telemetry resumes, remove warning and resume fresh-state handling automatically.
- **Not Present**: admin confirms car physically absent; no telemetry warning, no acknowledgment obligation. Presence is independent of connectedness.
- **Agreed PC control cadence: 50 Hz (20 ms).** In each control tick, poll the USB HID gamepad, apply the car-command rules, and generate/submit one shared World State. Display redraw is independently paced at 30/60 fps; video/rendering must not delay or clock this loop. E2's 100 Hz polling was experimental. Car telemetry is nominally **20 Hz**. Send topology and movement bytes continuously even if values have not changed; actual per-car BLE delivery is governed by modem scheduling.
- Read each car's zero-based `forward_button`, `left_button` and `right_button` from `[car_N_control]` in `config/address.ini` (currently cars 1–4 use button groups 0–2, 3–5, 6–8 and 9–11). The legacy `[joystick]` COM metadata is not used to open or identify this HID device.
- Preserve the existing wire layout: World State `<HB4B` is **7 bytes**; E15 Robot State `<BHHB4sHBBBhhH` is **21 bytes**, including all three state bytes after NFC age. The corrected Python format fixes documentation only; no packet fields or firmware have changed. See `INTERFACES.md` for offsets and USB framing.
- Normal car commands are `AUTO` plus forward/turn signals derived from the filtered input. In AUTO, absence of the forward bit means stop, **not** a separate STOP message. Preserve AUTO bit when forcing stop. On lost telemetry or joystick input device failure, zero forward/turn bits for affected cars; do not stop the shared World State broadcast. Firmware already implements its own World State watchdog; do not reimplement it on the PC.
- When the joystick controller drops, all four cars stop and robot continues; on recovery, restore car control from fresh inputs. Resume immediately from currently held inputs once communication/input is fresh and existing drive-eligibility checks pass; do not require release or a fresh button press. Discuss telemetry-loss thresholds when implementing each component; prefer silent recovery with diagnostic records where appropriate.
- Car firmware owns physical center/edge following, motor regulation, NFC reading and local protections. The PC owns all tag attributes, branch/default selection, reservations and topology decisions. No navigation graph, firmware map dictionary or local topology enforcement is required. E16 should remove E15's fixed tag-cycle restriction while preserving the wire protocol and local protections; see `E16_FIRMWARE_CHANGES.md`. No firmware implementation/flashing is authorized by this plan.

## 5. PC-owned NFC tag attributes and intersections
Use a UID-to-attributes dictionary distilled from Rhino, with approximately 300 physical tags. No adjacency graph, route planner, branch-destination graph or firmware map export is required. Visual position/orientation metadata may accompany tags for the minimap without introducing navigation edges. Final JSON serialization/export is reviewed when the file is supplied.

| Attribute | Values | Meaning |
|---|---|---|
| `track` | 1, 2, 3, 4, none | Track membership for monitoring/admin recovery, not automatic rerouting |
| `mergeedge` | left, right, none | Force the indicated following edge in AUTO; no merge HUD required |
| `split` | left, right, leftright, none | Normal upcoming split, HUD options and edge selection |
| `adminsplit` | left, right, leftright, none | Admin-only branch choice; normal mode must use `safeexit` |
| `inzone` | A, B, C, D, none | Current zone occupancy context |
| `reservezone` | A, B, C, D, none | Zone token requested while this context persists |
| `safeexit` | left, right, none | Forced exit when admission is denied, at a normal-mode adminsplit, or during approach evacuation |

`none` here is a semantic value; its JSON representation is not yet frozen. Tags on tracks 1/2 carry the zone attributes for A/B and C/D respectively; tracks 3/4 do not grant access to those zones. An encountered track mismatch is diagnostic information, not permission to change a car's assigned zones.

- On a new distinct NFC UID from accepted, ordered telemetry, replace the car's complete navigation context with that tag's attributes. Context persists until the next distinct UID. Repeated same-UID telemetry does not repeat transitions, release tokens or restart timers; it still updates telemetry health. A UID may be processed again after an intervening distinct UID.
- An **unknown but actually observed UID is an ordinary tag with every attribute none**, including token-release eligibility. Log the unknown UID for map diagnostics. A malformed telemetry frame, no-read/startup sentinel, communication loss or age increase is not an observed unknown tag. Reboot/initial localization handling remains a recovery checkpoint.
- A new tag qualifies as **out of zone/token release if and only if `inzone:none` AND `reservezone:none`**. It clears the car's token and completes evacuation where applicable. `track`, split and merge attributes do not alter this predicate. No explicit release attribute or graph traversal is needed. Merely losing contact with a tag does not release anything.
- Use 2-3 approach tags per split and about 2 tags before merges. Consecutive approach UIDs can refresh equivalent context without releasing an existing token or resetting reservation timers. The user accepts missed steering-reset tags on ordinary single-line roads: continuing an edge-following command there is acceptable. Do not introduce a localization fault solely for lack of NFC progress or missed tags. Zone release still requires an observed qualifying tag.
- Recompute filtered commands each 50 Hz tick, even without a new UID: joystick/admin input, reservation availability and evacuation can change while context stays fixed. Denied reservation requests continue while `reservezone` remains set, allowing the player to wait for the robot to clear the zone. A denied request does not itself force forward movement.

Normal split edge selection (forward enable remains controlled separately):

| Split | Left input | Neutral input | Right input |
|---|---|---|---|
| left (left/straight) | left edge | right edge | right edge |
| right (straight/right) | left edge | left edge | right edge |
| leftright | left edge | left edge | right edge |

After sanitizing incoherent physical inputs, reservation denial overrides branch selection with `safeexit`. In normal mode, `adminsplit` also forces `safeexit`; in admin AUTO it exposes branch choices using the same split table instead. **Admin does not bypass normal `split` zone-token admission:** any zone entry still requires its token. `mergeedge` forces its indicated edge in AUTO. With no active split/adminsplit or merge context, clear both turn bits regardless of input. MANUAL retains existing direct wheel controls for admin recovery, not AUTO filtering; it does not grant/release a zone token. Detailed physical recovery remains operator-managed.

Validate tags before use: `reservezone` and `adminsplit` require a usable `safeexit` where forced exit is possible; conflicting merge/split declarations need correction rather than an invented precedence. HUD shows raw input and contextual split choices; merge forcing needs no HUD indicator. Car positions remain at the last observed registered marker without interpolation; an unknown UID supplies no invented position.

## 6. Topology and zone reservations
- `topology_id` is the **existing single byte**, now interpreted as **effective zone availability**: bit0 A, bit1 B, bit2 C, bit3 D (1=available), bit4 admin mode, bits5–7 reserved. A zone is available to its car only when the board is present and robot has not acquired/exclusively closed the zone. Car reservations are managed by central PC state, not conveyed in extra packet fields.
- Each zone has at most one allowed car competitor: A/B ↔ Car1, C/D ↔ Car2. Cars 3/4 never request these zones. In normal conditions, cars have priority over an available zone. The robot requests it back before moving in.
- At the first approach context for an accessible zone, request its token; if denied, retry each control tick while that same `reservezone` context remains. Grant only when the board is present and the robot has neither acquired nor closed/pending-claimed the zone. Until granted, filter steering to `safeexit`; the player may stop and wait, then obtain the token without crossing another tag. One car may hold at most one zone token; do not replace it silently when a different request appears. A granted token persists across approach/inside tags and is released only by a new tag satisfying `inzone:none` AND `reservezone:none`, including observed unknown tags. Retries and repeated approach tags never restart token-holding timers. Admin mode does not bypass zone admission. An inside-zone observation without the corresponding token is a reconciliation fault, not automatic retroactive admission.
- Robot scheduling only considers occupied board zones without a car reservation. On request, mark robot acquisition pending; set zone availability bit off and transmit changed topology. After acknowledgment from required Present cars, grant robot access. If a car holds reservation, do **not** flip its availability bit or grant robot ownership; choose another eligible zone. Car/robot conflicts are settled centrally in a deterministic event order.
- **Acknowledgment:** retain the existing receipt synchronization gate using the first `world_seq` containing changed topology **and PC-filtered movement commands consistent with that closure**. Wait for fresh wrap-safe `last_world_seq` echoes from required cars. There is no firmware map/topology application to acknowledge: the echo establishes receipt only, not physical clearance or a branch taken. PC tokens/occupancy and the existing accepted timing trade-off govern robot admission; do not claim the echo independently proves safe navigation.
- For a Present but telemetry-silent car, apply the agreed **last-known-state exception**: last known outside with no reservation does not block the robot; last known approach/inside keeps reservation. This is explicitly not a formally race-free distributed interlock.
- Robot keeps its zone ownership through entry, pickup/place and retreat, releasing it **at verified high clearance**, before returning home. Empty zones never become available to cars simply because the robot releases ownership.
- Exact no-collision proof at point of commitment was discussed but deliberately **not** adopted: the design accepts a small latency race with slow cars/redundant approach markers; avoid claiming industrial safety-grade mutual exclusion. The UR physical safety system remains independent.

## 7. Automatic car evacuation
For a car holding a reservation, start two independent monotonic timers at first grant: (i) time since last forward joystick input, default **10 s**, reset whenever forward is commanded; (ii) total holding duration, default **60 s**, never reset. Repeated tags, denied requests and idempotent grants do not reset these timers. Either expiry starts visitor-noninterruptible `EVACUATING`:

- In approach context (`inzone:none`, `reservezone` set), hold AUTO + forward and force the tag's `safeexit` direction.
- Inside a zone (`inzone` set), hold AUTO + forward without a forced turn; apply `mergeedge` if present. Ignore visitor turn intent during evacuation.
- Reevaluate against each distinct tag's context. Continue until a new observed tag has **both `inzone:none` and `reservezone:none`**, then release the token, end evacuation and restore visitor input. An observed unknown tag meets this condition. An approach tag with `inzone:none` alone does not.

The physical route/tag labeling must support these exits. Admin stop, communication loss and firmware protections retain precedence. On a bounded evacuation failure timeout, stop driving and retain the token for admin handling. Lack of NFC progress while a visitor holds forward is not itself a fault. How timers pause/resume in admin mode remains a component-specific implementation discussion.

## 8. Board inventory and scheduling
- Exactly three boards exist across A–D plus gripper. When gripper empty, three zones occupied and one empty; during transfer, gripper holds one board and two zones are empty.
- At home with gripper empty: select occupied eligible pickup zone. At home carrying board: select empty placement zone **other than its known pickup zone**; normally this is the pre-transfer empty slot. On a startup with an already-held board and unknown source, either empty zone is eligible.
- Policy is a **replaceable least-recently-touched queue** initially `[A,B,C,D]`. Scan queue for first occupied eligible pickup. Move zone to back only after successful pickup or placement; skip blocked zones without altering queue. This naturally prefers avoiding the most recently placed board but is a **soft preference**. If no eligible pickup exists, wait at home and retry.
- Reservation safety/eligibility stays outside the scheduler; a selected move must be revalidated before authorizing robot motion. Administrator recovery must reconcile physical and logical board states.

## 9. Robot movement, tool and taught targets
- Four zone targets and one common HOME. For each zone store a **taught six-joint target** (initially placeholder only), derive low/high approach poses using forward kinematics and world/base +Z offsets, with inverse kinematics near the taught configuration. Installation and insertion are along world/base **−Z**, retraction along **+Z**.
- Motion pattern: HOME → high clearance → low approach (position-controlled, relatively fast) → installation (slow/force-controlled) → low approach/high clearance → HOME. **Release zone token only at verified high-clearance pose**, not necessarily at home. Verify full arm/gripper/board envelope, not only TCP height.
- **Pickup:** engage tightening screw and apply approx. 10 N downward force simultaneously. Success requires *both* reaching target Z depth and tool reporting screw stall; a stall **before** target depth is immediate failure. Stop actuation and force mode on failure. Successful pickup changes board inventory/payload; return via valid clearance path.
- **Placement:** descend in force mode to target Z, initiate unscrewing and immediately apply approx. 5 N upward force concurrently; stop unscrewing and force mode upon reaching specified upper Z, then finish position-controlled retreat. No independent unscrew-finished signal is required.
- Robot uses built-in FT sensor; configure mass/centre of mass for empty gripper and board-loaded states, gravity compensation, contact force, timeouts, travel bounds, speed and physical validation. Configuration and completion criteria require live tuning.
- Tool uses **existing, tested URCap → RS-485** command path. Permit real tool communication testing while robot movements stay dry-run. Development-mode tool tests may bypass *mechanical pickup stall completion* (e.g. bounded motor run) but must never mislabel a mechanical pickup as successful or disable motor protections. Production pickup requires both conditions. Implement development-mode bypass distinctly from production mode.
- Failures: record stage, target, tool and board inventory, retain token until robot clears it; car subsystems continue. Admin recovery through app should reuse validated high-level motion/tool primitives (`retract`, `return home` if valid, `retry`, `tool controls`, `resume`), no unrestricted jog initially. Automatic failed-pickup retry (unscrew/back off/retry limited times) is deferred. Robot protective-stop reset policy is **unresolved**, not permission for unattended reset.

## 10. Administrator, displays and logging
- Admin PC UI: startup board inventory; car Present/Not Present (Not Present is physical-removal assertion); per-device diagnostics; robot status and context-appropriate recovery; robot dry-run/live and tool development mode; car status, topology bits, current reservations and queue. Keyboard and mouse access is administrator-only. Agreed controls are in section 12; visual layout remains to be designed.
- Each of four monitors is dedicated to one car: responsive low-latency FFmpeg-backed Wi-Fi FPV, fixed full-map **axonometric** minimap, and HUD for raw forward and left/right joystick states, contextual branch options and later telemetry. Video, UI and control independently update.
- Minimap: own car prominent; other cars ghosted; all markers remain at last known tag; six prerendered car sprites (four compass orientations + uphill + downhill). Confirm geometric orientation needs during map build. Show current boards and dynamic route availability (orange accessible, grey unavailable, optional cross for blocked branches); overlay context-specific intersection choices. Pre-rendered map/path assets likely, detailed compositing design deferred.
- Log warnings for telemetry gaps without hiding last marker; allow physically Not Present cars without warnings. Preserve diagnostics for packet loss, echo age, device connectivity, NFC, robot and tool events.

## 12. Agreed admin, recovery and deferred work

### Admin mode and keyboard control
- On leaving admin mode, immediately resume visitor control from currently held, freshly sampled inputs; no release/fresh-press gate. The same rule applies after gamepad/car communication recovers, once fresh observations and existing drive-eligibility checks pass. Never replay stale cached commands or infer that recovery clears reservations or firmware protections.
- Space toggles normal/admin mode; Escape cancels the current admin action. Keyboard and mouse are accessible only to the administrator. Admin input must reach the central controller regardless of which display has focus; detailed focus/mouse behavior is reviewed with the UI implementation.
- In admin mode, visitor gamepad inputs have no effect. Video, UI, telemetry handling and the 50 Hz World State loop continue. All visitor screens show **Game Paused / Admin Control**. This overlay is not evidence that every physical subsystem is stopped.
- Keys 1-4 select a car. Up/Left/Right control it in AUTO using current firmware behavior. While **Left Ctrl is held**, the selected car uses MANUAL mode and Down allows reverse; releasing Left Ctrl returns to AUTO. Do not carry stale movement intent across selection/mode changes.
- Only the selected car receives admin driving intent; public inputs are ignored. Existing stop/fault rules remain authoritative. Keep the firmware's simultaneous-turn behavior: the PC filters incoherent physical input before generating movement bytes. Deliberate following-mode encoding is distinct from contradictory physical input.
- Read shortcuts from the existing `[admin_keyboard_shotcut]` INI section. Space toggles modes; Escape cancels the current admin action; Q requests controlled exit. E9's immediate Escape/Q/group-exit behavior must not become production behavior. No new firmware behavior for topology admin bit 4 is assumed.
- Initial car selection, detailed transition/recovery rules and whether autonomous robot scheduling and evacuation timers continue or pause during admin mode are discussed when implementing those components.

### Controlled application exit
- Stop scheduling new board-transfer cycles and suppress visitor driving. Keep control connections/UI alive while the robot completes the required validated clearance/return sequence. Close connections/displays and quit **only after verified HOME**, not after merely sending a home command.
- Discuss active screw operations, held or partly attached boards, robot disconnection and protective stops at the robot/shutdown milestone. If HOME cannot be verified, show blocked shutdown and request operator intervention; do not silently quit or force an unvalidated trajectory. Cancellation/forced-exit policy remains unspecified.

### Component-specific recovery
- Prefer silent automatic recovery for ordinary disconnects where appropriate, retaining timestamped diagnostics. Ask the user targeted questions when implementing each component instead of requiring all recovery policies now.
- Prioritize **toy cars powered off for charging and reappearing afterward**. Before implementing this, discuss reboot/reappearance detection, fresh localization/topology synchronization, control reenable and reconciliation of retained reservations. Temporary disconnection is not operator-confirmed Not Present and must not automatically clear zone ownership.

### Deferred map and early tool experiment
- Tag semantics are agreed in sections 5-7. The user will provide Rhino JSON; defer final serialization, visual metadata, export and registration implementation until that file is reviewed. No graph or firmware map export. A small explicitly synthetic fixture can support unrelated tests without becoming the final schema.
- Plan 2-3 approach tags per split, sharing the same upcoming-intersection meaning, so one missed tag is tolerated. Repeated approach tags do not release reservations. This is redundancy, not a guarantee for missing every approach tag; validate physical behavior later.
- Before main tool integration, plan a small screwdriver communication/behavior experiment covering actual commands, direction, stop, status/stall reporting, timeout and cancellation. Keep UR motion dry-run and review bounded live tool operation with the operator before running it. Mechanical attachment success is a separate validation.
