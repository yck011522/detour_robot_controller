# deTour scaffolding game controller — functional specification

**Status:** working requirements baseline from design discussions, 2026-11-05. This document records intended behavior, including some features not yet implemented in E15. It is not authorization to modify tested firmware.

## 1. Purpose and physical system
A Windows PC coordinates a UR10e robot that repeatedly transfers **three identical floorboards among four installation zones (A–D)**; four independent visitor-operated line-following cars on the scaffolding, up to four dedicated FPV displays; the single USB HID gamepad tested in `experiments/e2_gamepad_controller.py` for all player inputs; a USB-serial BLE modem which relays World State to cars and telemetry to the PC; and a screw-based robot gripper commanded through an existing URCap/RS-485 path. Car 1 alone accesses Zones A,B; Car 2 alone accesses Zones C,D. Cars 3 and 4 have no movable-board zones. Each zone may be used by the robot or its designated car, never both at once.

## 2. System ownership and modules
- **Device adapters:** USB HID gamepad through Pygame, BLE modem transport, robot motion/UR controller, URCap screwdriver, FPV video sources, displays. Physical-device and synthetic/dry-run variants must expose comparable application-level contracts.
- **Central game state:** authoritative board location (A–D, gripper), robot operation phase, per-car presence/telemetry/location/reservation, zone ownership, effective availability bits and World State version/sequence tracking.
- **Car command filter:** transforms raw three-button input (forward, left, right) into effective movement byte by operating state, NFC approach context and branch restrictions. Turning rules are intersection-contextual, **not direct raw joystick passthrough**.
- **Zone manager:** four small, centrally executed state machines; car reservations at approach markers; robot pending request, topology closure, acknowledgement and robot ownership; zone-clear release.
- **Pickup scheduler:** replaceable least-recently-touched queue; eligibility is determined independently of preference.
- **Robot task executor:** reusable validated motion primitives and tool coordination, invoked by scheduler or context-limited administrator recovery.
- **Presentation:** four separately rendered screens, shared map/game model; video and rendering cannot block control loops.
- **Diagnostics and logging:** record all state changes, faults, commands, World State submissions/echoes and reservations with monotonic timestamps.

## 3. Modes, startup and shutdown
There is **STARTUP → NORMAL_OPERATION**; no separate READY state is required. Subsystems may be paused, disconnected or faulted independently without necessarily stopping the whole exhibition. A global stop or controlled shutdown may be implemented with explicit behavior; don't infer that PC software replaces UR safety functions.

Startup gates:
1. Read INI. Connect the configured **modem COM port** and initialize the **USB HID gamepad through Pygame**, validating the `[car_N_control]` button mappings. If either is unavailable, report the failure and **quit**: include configured/available COM ports for modem failure, or enumerated gamepads and mapping errors for input failure. No joystick COM connection or serial framing is involved. Final HID identity/selection rules still need agreement; no automatic COM-port selection UI.
2. Establish and diagnose UR and its existing URCap/RS-485 gripper communication. Test availability without unintended motion.
3. Administrator selects **exactly three** board locations among checkboxes `A`, `B`, `C`, `D`, `GRIPPER`. That is the authoritative initial board inventory.
4. Perform **operator-assisted homing**: the operator visually verifies clearance and authorizes carefully controlled robot motion to a known home waypoint. Account for held-board geometry and payload. Block startup until homing succeeds. Homing after a restart does not automatically resume interrupted trajectories.
5. Administrator visually confirms **both token-participating cars are outside zones**, initializing their car reservations to `None`. Presence/Not Present is independently selectable per car; Not Present means physically removed, explicitly confirmed by operator.
6. Compute initial zone availability; broadcast and synchronize topology for relevant Present cars as applicable. Only then start NORMAL_OPERATION.
7. If gripper holds a board, enter `SELECT_PLACEMENT`; else enter `SELECT_PICKUP`. When starting with a held board, either of the two empty zones may receive the first placement; no unknown source zone needs exclusion.

During normal operation, modem port loss is **auto-retried only on the configured COM port**. Gamepad disconnection/reconnection is handled through Pygame's HID/joystick lifecycle as in E2, with final device matching and input reenable policy to be agreed. Robot assembly may continue when joystick or modem communication fails, subject to independent robot state and reservation rules.

## 4. Car presence, telemetry and command flow
- **Present**: telemetry expected; missing telemetry retains last known NFC/zone reservation; warning displayed after configurable threshold. If last known outside and no reservation, robot may acquire the zone without fresh acknowledgment (deliberate operational trade-off). If last known approaching/inside, retain reservation. When telemetry resumes, remove warning and resume fresh-state handling automatically.
- **Not Present**: admin confirms car physically absent; no telemetry warning, no acknowledgment obligation. Presence is independent of connectedness.
- **Agreed PC control cadence: 50 Hz (20 ms).** In each control tick, poll the USB HID gamepad, apply the car-command rules, and generate/submit one shared World State. Display redraw is independently paced at 30/60 fps; video/rendering must not delay or clock this loop. E2's 100 Hz polling was experimental. Car telemetry is nominally **20 Hz**. Send topology and movement bytes continuously even if values have not changed; actual per-car BLE delivery is governed by modem scheduling.
- Read each car's zero-based `forward_button`, `left_button` and `right_button` from `[car_N_control]` in `config/address.ini` (currently cars 1–4 use button groups 0–2, 3–5, 6–8 and 9–11). The legacy `[joystick]` COM metadata is not used to open or identify this HID device.
- Preserve the existing wire layout: World State `<HB4B` is **7 bytes**; E15 Robot State `<BHHB4sHBBBhhH` is **21 bytes**, including all three state bytes after NFC age. The corrected Python format fixes documentation only; no packet fields or firmware have changed. See `INTERFACES.md` for offsets and USB framing.
- Normal car commands are `AUTO` plus forward/turn signals derived from the filtered input. In AUTO, absence of the forward bit means stop, **not** a separate STOP message. Preserve AUTO bit when forcing stop. On lost telemetry or joystick input device failure, zero forward/turn bits for affected cars; do not stop the shared World State broadcast. Firmware already implements its own World State watchdog; do not reimplement it on the PC.
- When the joystick controller drops, all four cars stop and robot continues; on recovery, restore car control from fresh inputs. Exact neutral-input reenable policy and telemetry-loss thresholds are configurable/unresolved until tested.
- Car firmware owns physical line following, branch execution, motor regulation, NFC reading and its local failsafes. PC owns graph meaning, command filtering, reservations and topology decisions. A forthcoming car firmware iteration will need to understand the shared map and enforce branch restrictions locally; **no firmware modification is authorized yet**.

## 5. NFC map and intersections (intended future firmware behavior)
- Approx. **300 physical tags**, identified by raw UID. The map dictionary should assign stable logical marker IDs, tag classification, zone association, intersection identity/type and branch destinations; static graph separate from dynamic availability. Detailed Rhino/Grasshopper schema is deferred.
- Only three **two-output** splits: `SPLIT_LEFT` (left/straight), `SPLIT_RIGHT` (straight/right), `SPLIT_LR` (left/right). There is NO left/straight/right three-way split.
- Multiple (nominally two or three) **approach tags** may refer to the same upcoming split to tolerate skipped NFC readings. Their approach meaning must persist; repeated detections and subsequent approach tags must not release a reservation.
- Other tag meanings include `INSIDE_ZONE` and `OUTSIDE_ZONE`, including non-zone intersections. **A qualifying OUTSIDE tag downstream of a split clears the reserving car's reservation**, across all zones assigned to that car. Approach tags, though physically outside, are not OUTSIDE release tags. Many downstream outside tags provide natural redundancy.
- Latest successfully read NFC UID persists in telemetry; its age allows identification of a fresh observation versus a stale repeated last-seen UID. Visual car positions jump discretely between tags; no interpolation or stale-position dimming. A missed tag simply means a jump to the next observed location; the PC does not treat lack of NFC progress as a fault.
- Joystick left/right signals are initially **displayed raw** but sent to car only after context-aware filtering at an upcoming split. Default branch choices map to the **edge-following command**, not necessarily the corresponding physical label: `SPLIT_LEFT` center/straight → right-edge following; left → left-edge following. `SPLIT_RIGHT` is mirrored. `SPLIT_LR` has no center route; default one direction (currently proposed left), subject to topology.
- PC filters out blocked branches; car firmware will independently lock to the permitted branch using the received availability bits and local NFC dictionary. Once a split's approach sequence is recognized, the intended firmware should maintain the selected following mode until an appropriate non-intersecting marker. How to handle mid-approach choice/topology changes is a firmware-design checkpoint, not a preauthorized implementation.

## 6. Topology and zone reservations
- `topology_id` is the **existing single byte**, now interpreted as **effective zone availability**: bit0 A, bit1 B, bit2 C, bit3 D (1=available), bit4 admin mode, bits5–7 reserved. A zone is available to its car only when the board is present and robot has not acquired/exclusively closed the zone. Car reservations are managed by central PC state, not conveyed in extra packet fields.
- Each zone has at most one allowed car competitor: A/B ↔ Car1, C/D ↔ Car2. Cars 3/4 never request these zones. In normal conditions, cars have priority over an available zone. The robot requests it back before moving in.
- Car reservation is established at **first approach NFC marker** for its accessible zone, persists across all approach and inside markers, and is cleared at a subsequent qualifying OUTSIDE marker. A car can reserve at most one zone. If robot already owns the zone and topology blocks entry, approach markers must not override robot ownership; the car must take the bypass.
- Robot scheduling only considers occupied board zones without a car reservation. On request, mark robot acquisition pending; set zone availability bit off and transmit changed topology. After acknowledgment from required Present cars, grant robot access. If a car holds reservation, do **not** flip its availability bit or grant robot ownership; choose another eligible zone. Car/robot conflicts are settled centrally in a deterministic event order.
- **Acknowledgment:** record first `world_seq` generated with the changed topology and wait for `last_world_seq` from relevant cars to equal/pass it, accounting for 16-bit wraparound and sequence freshness. User considers receipt acknowledgement sufficient for topology acceptance; new car navigation firmware must apply topology immediately on receipt. `last_world_seq` itself is a receipt echo, not a physical-clearance sensor.
- For a Present but telemetry-silent car, apply the agreed **last-known-state exception**: last known outside with no reservation does not block the robot; last known approach/inside keeps reservation. This is explicitly not a formally race-free distributed interlock.
- Robot keeps its zone ownership through entry, pickup/place and retreat, releasing it **at verified high clearance**, before returning home. Empty zones never become available to cars simply because the robot releases ownership.
- Exact no-collision proof at point of commitment was discussed but deliberately **not** adopted: the design accepts a small latency race with slow cars/redundant approach markers; avoid claiming industrial safety-grade mutual exclusion. The UR physical safety system remains independent.

## 7. Automatic car evacuation
For a car holding a reservation, start two independent monotonic timers at first reservation: (i) time since last forward joystick input, default **10 s**, reset whenever forward is commanded; (ii) total holding duration, default **60 s**, never reset. Either expiry starts a visitor-noninterruptible `EVACUATING` override: send AUTO + forward, no left/right, choosing the known default forward exit. The physical track guarantees an unobstructed forward route and multiple downstream OUTSIDE markers. Complete when a fresh qualifying outside-zone marker is observed, then release reservation and restore visitor input. Admin stop, loss of communication, or car firmware protection still take precedence. Set a bounded failure timeout; if unrecovered, stop driving and retain reservation for admin handling. Lack of NFC progress *by itself while visitor holds forward* is not a fault.

## 8. Board inventory and scheduling
- Exactly three boards exist across A–D plus gripper. When gripper empty, three zones occupied and one empty; during transfer, gripper holds one board and two zones are empty.
- At home with gripper empty: select occupied eligible pickup zone. At home carrying board: select empty placement zone **other than its known pickup zone**; normally this is the pre-transfer empty slot. On a startup with an already-held board and unknown source, either empty zone is eligible.
- Policy is a **replaceable least-recently-touched queue** initially `[A,B,C,D]`. Scan queue for first occupied eligible pickup. Move zone to back only after successful pickup or placement; skip blocked zones without altering queue. This naturally prefers avoiding the most recently placed board but is a **soft preference**. If no eligible pickup exists, wait at home and retry.
- Reservation safety/eligibility stays outside the scheduler; a selected move must be revalidated before authorizing robot motion. Administrator recovery must reconcile physical and logical board states.

## 9. Robot movement, tool and taught targets
- Four zone targets and one common HOME. For each zone store a **taught six-joint target** (initially placeholder only), derive low/high approach poses using forward kinematics and world/base +Z offsets, with inverse kinematics near the taught configuration. Installation and insertion are along world/base **−Z**, retraction along **+Z**.
- Motion pattern: HOME → high clearance → low approach (position-controlled, relatively fast) → installation (slow/force-controlled) → low approach/high clearance → HOME. **Release zone token only at verified high-clearance pose**, not necessarily at home. Verify full arm/gripper/board envelope, not only TCP height.
- **Pickup:** engage tightening screw and apply approx. 10 N downward force simultaneously. Success requires *both* reaching target Z depth and tool reporting screw stall; a stall **before** target depth is immediate failure. Stop actuation and force mode on failure. Successful pickup changes board inventory/payload; return via valid clearance path.
- **Placement:** descend in force mode to target Z, initiate unscrewing and immediately apply approx. 5 N upward force concurrently; stop unscrewing and force mode upon reaching specified upper Z, then finish position-controlled retreat. No independent unscrew-finished signal is required.
- Robot uses built-in FT sensor; configure mass/centre of mass for empty gripper and board-loaded states, gravity compensation, contact force, timeouts, travel bounds, speed and physical validation. Configuration and completion criteria require live tuning.
- Tool uses **existing, tested URCap → RS-485** command path. Permit real tool communication testing while robot movements stay dry-run. Development-mode tool tests may bypass *mechanical pickup stall completion* (e.g. bounded motor run) but must never mislabel a mechanical pickup as successful or disable motor protections. Production pickup requires both conditions. Implement development-mode bypass distinctly from production mode.
- Failures: record stage, target, tool and board inventory, retain token until robot clears it; car subsystems continue. Admin recovery through app should reuse validated high-level motion/tool primitives (`retract`, `return home` if valid, `retry`, `tool controls`, `resume`), no unrestricted jog initially. Automatic failed-pickup retry (unscrew/back off/retry limited times) is deferred. Robot protective-stop reset policy is **unresolved**, not permission for unattended reset.

## 10. Administrator, displays and logging
- Admin PC UI: startup board inventory; car Present/Not Present (Not Present is physical-removal assertion); per-device diagnostics; robot status and context-appropriate recovery; robot dry-run/live and tool development mode; car status, topology bits, current reservations and queue. Administrator keyboard support and exact shortcuts remain to be designed.
- Each of four monitors is dedicated to one car: responsive low-latency FFmpeg-backed Wi-Fi FPV, fixed full-map **axonometric** minimap, and HUD for raw forward and left/right joystick states, contextual branch options and later telemetry. Video, UI and control independently update.
- Minimap: own car prominent; other cars ghosted; all markers remain at last known tag; six prerendered car sprites (four compass orientations + uphill + downhill). Confirm geometric orientation needs during map build. Show current boards and dynamic route availability (orange accessible, grey unavailable, optional cross for blocked branches); overlay context-specific intersection choices. Pre-rendered map/path assets likely, detailed compositing design deferred.
- Log warnings for telemetry gaps without hiding last marker; allow physically Not Present cars without warnings. Preserve diagnostics for packet loss, echo age, device connectivity, NFC, robot and tool events.
